# AI K8s Platform v0.1.0 交付手册

v0.1.0 是当前已经验证可登录、无 license 阻断的工程基线。这个版本先固定 KubeSphere Core 的 Kubernetes 管理能力，前端 `console` 与后端 `kubesphere` 采用双仓库固定版本的方式管理，Apps/Extension 管理体系后续再拆。

## 代码仓库

- 后端与 Helm chart: `https://github.com/archinfra/kubesphere.git`
- 前端 Console: `https://github.com/archinfra/kubesphere-console.git`
- 固定版本: 两个仓库都使用 `v0.1.0` tag 作为首个可用基线。

这种双仓模式更接近原工程结构，也方便后续独立改造前端体验、后端 API、离线包构建和 AI Native 控制面。不要把前端硬拷贝进后端仓库，除非后续明确要做 monorepo；当前更推荐用 GitHub Actions 在构建时拉取指定的 console tag。

## 一键离线安装

在 GitHub Release 或 Actions artifact 下载对应架构的安装包，例如:

```bash
chmod +x ai-k8s-platform-v0.1.0-amd64.run
sha256sum -c ai-k8s-platform-v0.1.0-amd64.run.sha256
./ai-k8s-platform-v0.1.0-amd64.run install -y
```

默认行为:

- 安装 namespace: `kubesphere-system`
- Helm release: `ks-core`
- Console NodePort: `30880`
- 内网镜像仓库前缀: `sealos.hub:5000/ai-k8s-platform`
- 默认导入并推送镜像: `ks-apiserver`、`ks-controller-manager`、`ks-console`、`kubectl`、`redis`
- 默认关闭 telemetry 和 extension repository，避免离线环境访问外部服务。

如果目标集群使用自己的镜像仓库:

```bash
./ai-k8s-platform-v0.1.0-amd64.run install -y \
  --registry-repo harbor.local/library/ai-k8s-platform \
  --registry-username admin \
  --registry-password '<password>'
```

如果镜像已经提前导入目标仓库，只执行 Helm 部署:

```bash
./ai-k8s-platform-v0.1.0-amd64.run install -y \
  --registry-repo harbor.local/library/ai-k8s-platform \
  --skip-image-prepare
```

查看状态:

```bash
./ai-k8s-platform-v0.1.0-amd64.run status
kubectl get deploy,pods,svc -n kubesphere-system -o wide
```

卸载:

```bash
./ai-k8s-platform-v0.1.0-amd64.run uninstall -y
```

默认卸载会保留 CRD 和用户数据。实验环境需要彻底清理时再使用:

```bash
./ai-k8s-platform-v0.1.0-amd64.run uninstall -y --delete-crds
```

## 构建离线包

本地或远程构建机需要:

- Docker 或 Buildx
- Go
- Node.js 18 与 Yarn 1
- jq、tar、sha256sum

如果构建机同时存在多个 Node 版本，建议显式指定:

```bash
export NODE_HOME=/opt/node-v18.20.4-linux-x64
export PATH=/usr/local/go/bin:$NODE_HOME/bin:$PATH
```

GitHub Actions 默认使用公开基础镜像 `alpine:3.21.3` 和 `node:18-alpine`。如果构建机访问 Docker Hub 不稳定，可以切到内网基础镜像:

```bash
export BACKEND_BASE_IMAGE=sealos.hub:5000/kube4/busybox:v1
export CONSOLE_BASE_IMAGE=sealos.hub:5000/kube4/os-shell:12-debian-12-r51
```

手工构建:

```bash
git clone https://github.com/archinfra/kubesphere.git
git clone https://github.com/archinfra/kubesphere-console.git console
cd kubesphere
hack/release/build-offline-run.sh --version v0.1.0 --arch amd64 --console-dir ../console
```

产物位置:

```text
dist/ai-k8s-platform-v0.1.0-amd64.run
dist/ai-k8s-platform-v0.1.0-amd64.run.sha256
```

GitHub Actions 构建:

- 手动进入 `Build AI K8s Platform Offline Installer` workflow，输入 version、arch、console_repository、console_ref。
- 推送 `v*` tag 时自动按 `amd64`、`arm64` 构建并发布 Release。
- tag 构建默认使用 `https://github.com/archinfra/kubesphere-console.git` 的 `v0.1.0` tag。

## 开发与维护

日常开发优先使用远程开发机验证:

```powershell
powershell -ExecutionPolicy Bypass -File .\hack\ai-native\run-remote-dev-loop.ps1 -Stage access
powershell -ExecutionPolicy Bypass -File .\hack\ai-native\run-remote-dev-loop.ps1 -Stage smoke
```

常用阶段:

- `backend`: 后端测试与二进制构建。
- `frontend`: 前端依赖安装与生产构建。
- `images`: 构建本地开发镜像。
- `deploy`: Helm 部署到测试集群。
- `smoke`: 等待 rollout 并检查 API/Console。
- `access`: 打印访问地址、运行状态、admin 用户状态和最近登录记录。

版本维护建议:

- 每个可登录、可升级、可离线交付的状态都打 tag，例如 `v0.1.1`。
- 后端仓库 tag 与前端仓库 tag 保持一致。
- 修改 Helm values、镜像名、安装器参数时，必须重新跑 `status`、`smoke` 和一次干净集群安装。
- Apps/Extension 拆分不要混进 v0.1.x 的稳定基线，建议从 `v0.2.0` 开始单独做模块边界和开关。

## 后续 AI Native 路线

v0.1.0 只负责把平台稳定交付。下一阶段再在这个基线上增加:

- Agent 可调用的安全 API 门面。
- 集群只读诊断、变更计划、审批执行三段式工作流。
- 操作审计、回滚快照和风险分级。
- 面向大模型的 Kubernetes 资源摘要、事件归因和修复建议。

这能避免一边补交付链路、一边大改业务能力，工程风险更可控。
